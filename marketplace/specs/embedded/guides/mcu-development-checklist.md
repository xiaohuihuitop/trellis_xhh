# MCU 开发检查清单

> 本清单定义 MCU 固件开发后的审查契约。先输出按严重度排序的问题，再给修改建议；不得只给出“看起来没问题”的结论。

---

## 审查输出要求

### 严重度

| 级别 | 含义 | 处理要求 |
|------|------|----------|
| `P0` | 可能无法编译、越界、损坏 Flash、损坏数据或造成非预期硬件动作 | 必须修复后才能结束任务。 |
| `P1` | 功能逻辑、跨模块协议、配置或硬件事实不一致 | 必须修复，或由项目负责人明确确认其设计意图。 |
| `P2` | 规律性异常、可维护性风险或证据不足 | 必须说明风险，并由项目负责人决定是否处理。 |

### 每个问题必须包含

```text
[P1] 问题标题
位置：<相对文件路径>:<行号>
检查路径：
1. <起点：定义、配置或发送端>
2. <中间传递、计算或调用>
3. <终点：实际分支、状态、硬件操作或持久化结果>
证据：<关键常量、实值代入、数量或代码片段说明>
影响：<会出现的确定行为或风险>
建议：<最小修改方向>
```

- 问题必须给出代码或工程配置位置；仅有 README 缺项时，位置写 README 的相关标题或“缺少 `<标题>`”，并给出对应代码位置。
- 检查无异常时，仍必须列出检查路径、覆盖范围和结论，例如“检查 12 个 Trigger、12 个对应 `case`、4 条实值链路”。
- 未在 README、原理图或项目配置中找到必要事实时，不得猜测数值；报告为待确认项，并要求补齐资料。
- 检查工具只报告证据和建议，不自动修改硬件配置、阈值、Flash 地址或业务语义。

---

## 必须检查项

### 1. 状态等级、映射表与数值边界

**适用**：电池等级、UI 图标、告警级别、档位、协议枚举、标定表。

检查路径：

1. 定位枚举、宏、配置表或阈值表，记录状态集合及数量。
2. 追踪状态在 UI、协议、Flash、Task 和事件中的所有映射表或 `switch` 分支。
3. 比对数量、顺序、名称和业务含义；检查重复项、跳号、缺项和未覆盖的默认分支。
4. 对具备物理含义的边界做实值校验：例如 BAT 工作分格的 `LEVEL_0` 对应百分比必须为 `0`，阈值必须单调，最小值不得大于最大值。

以下异常至少报 `P1`：5 个电池等级只存在 4 个 UI 显示分支；同一等级在协议和 UI 中含义不同；等级 0 对应非 0 百分比。

### 2. 命名、表项与成对操作规律

**适用**：连续编号的宏/枚举/表项，`Start/Stop`、`Enable/Disable`、`Open/Close` 等成对接口。

检查路径：

1. 搜索连续命名序列，列出完整序列及编号。
2. 检查跳号、重复编号、重复值和数组索引是否一致，例如 `xx_1`、`xx_2`、`xx_3`、`xx_5`、`xx_5`。
3. 搜索成对操作的所有调用点，沿状态变量或资源句柄追踪启用、停止和释放路径。
4. 仅在能证明重复启动、漏停止或错误配对时报告问题；不得只凭函数名猜测行为。

### 3. Event 编解码与实值链路

**适用**：`xhh_Event_Trigger(...)`、`xhh_Event_Handle(...)`、事件参数的来源 ID 与业务数据编码。

检查路径：

1. 逐个定位 `xhh_Event_Trigger(...)`，记录事件、参数高位来源、低位业务数据、掩码和移位方式。
2. 逐个定位对应的 `case xhh_Event_xxx`，记录参数解析、来源判断及最终调用。
3. 核对发送与接收是否对称；来源 ID 与业务数据共用参数时，来源判断必须使用位掩码，不允许直接以整个参数全等比较来源 ID。
4. 对每个关键命令至少完成一次实值代入：发送端常量/拼接 -> Trigger 参数值 -> Handle 解析 -> `case` 命中 -> 实际状态变化。

实值代入必须给出具体值，例如 `0x11110002`，并逐段解释来源和业务数据如何被解析。事件为单槽设计时，还应检查短时间内多个 Trigger 的覆盖是否符合该事件的业务语义；只有覆盖造成业务丢失时才报 `P1`。

### 4. 数组、缓冲区与整数计算边界

**适用**：数组、协议帧、字符串、FIFO、`memcpy`、`memset`、`snprintf`、ADC 换算、时间累计和移位。

检查路径：

1. 从数组定义、缓冲区容量或结构体字段长度开始，追踪所有下标、长度参数和循环上界。
2. 核对下标范围是否为 `[0, size - 1]`，长度是否不超过目标容量，循环边界是否与数组长度一致。
3. 检查源与目标的 `memcpy/memset/snprintf` 长度、字符串终止符和协议长度字段。
4. 对乘除、移位、符号转换和时间差计算，验证中间表达式宽度、溢出、回绕和单位换算。

数组越界、长度可被外部数据突破、截断导致协议错误、`uint16_t` 乘法溢出等属于 `P0`。

### 5. Flash 地址、布局与写入约束

**适用**：`xhh_BSP_Flash_Erase/Read/Write`、链接配置、Flash 数据布局、升级或参数保存。

检查路径：

1. 从 README、Project Target、链接脚本或 Scatter 文件获得 MCU Flash 起始地址、容量、应用区和保留区。
2. 枚举全部 Flash 绝对地址、读写长度和结构体大小，推导实际访问区间。
3. 核对访问区间未越过 MCU Flash、应用区和保留区；检查擦除页边界、写入粒度、地址对齐及跨页行为。
4. 核对写入前的擦除流程、掉电或失败时的数据有效性处理，以及读取后的版本/字段校验。

Flash 地址无法从硬件资料确认时，报告 `P1` 待确认；地址或长度明确越界、覆盖程序区或违反擦写粒度时报告 `P0`。

### 6. README 硬件与产品事实一致性

**适用**：MCU、时钟、引脚、ADC、Timer/DMA、Flash、超时、阈值、低功耗与产品行为。

检查路径：

1. 从 README 提取明确的数值、映射和行为定义。
2. 在 `Project/`、`Platform/`、`xhh_BSP/`、`Components/` 和 `xhh_Module/` 中定位实际实现。
3. 对每一项建立“README 定义 -> 工程/BSP 配置 -> 代码使用点”的实值链路。
4. 代码具有明确产品行为但 README 未定义时，报告待确认并要求补齐，例如自动关机代码为 20 分钟、README 未说明或写为 5 分钟。

代码与 README 不一致属于 `P1`；缺少关键硬件事实导致无法核对时也属于 `P1`，不得自行选择其中一个值。

### 7. 构建目标、链接容量与产物

**适用**：全部 MCU 源码修改。

检查路径：

1. 确认实际 IDE Target、MCU 宏、启动文件和链接配置与 README 的 MCU 定义一致。
2. 执行当前项目的全量编译，记录错误、警告和生成的 `hex/bin` 路径。
3. 检查 RAM/Flash 使用量、链接警告和栈空间风险；无法从当前工具链得到栈信息时，明确记录覆盖限制。
4. 核对提交的 `hex/bin` 由本次构建生成，而非历史产物。

编译错误、目标 MCU 不一致、产物缺失属于 `P0`；新增警告或容量接近上限属于 `P1`。

### 8. GPIO 安全态、时钟和周期

**适用**：GPIO、PWM、UART、ADC、Delay、Timer、超时和周期 Task。

检查路径：

1. 对电机、电源、背光、使能、片选等输出，追踪复位后的默认电平、GPIO 配置顺序和首次写入时机。
2. 从系统时钟配置推导 Timer/PWM/UART/Delay 的真实频率，并与代码参数和 README 核对。
3. 从 `main.c` 或 `main_task.c` 的调度入口追踪 `Process_10ms` 等函数的实际调用周期，核对函数名、注释、计数逻辑和真实周期。
4. 对 `ms/us/s/min` 转换给出至少一个实值代入，确认超时、占空比和波特率未发生数量级错误。

上电即可能误动作的 GPIO 初始态属于 `P0`；频率、单位、周期或超时不一致属于 `P1`。

### 9. 中断与共享状态

**适用**：IRQ、回调、DMA 完成标志、主循环与 ISR 共享变量。

检查路径：

1. 枚举 ISR、回调和中断标志，定位清除标志、数据搬运和唤醒主循环的位置。
2. 追踪 ISR 与主循环共享的变量，检查是否使用 `volatile`，以及多字节访问、读改写操作是否需要临界区。
3. 检查 ISR 中是否存在阻塞延时、Flash 擦写、长循环、复杂协议解析或直接执行重业务逻辑。
4. 验证中断标志的清除时机不会造成重复进入或漏事件。

ISR 可能阻塞、标志未清、共享状态会产生确定竞争时属于 `P0`；证据不足但存在并发风险时报告 `P1` 并说明未覆盖条件。

### 10. 低功耗与恢复路径

**适用**：Sleep、Shutdown、自动关机、显示关机、唤醒和电源控制。

检查路径：

1. 追踪关闭顺序：功能停止 -> 外设关闭 -> 引脚安全态 -> MCU 低功耗。
2. 核对唤醒源、唤醒后时钟和外设恢复路径。
3. 对显示、通信和电源外设，核对数据手册要求的关闭步骤。
4. 检查是否具备冷上电自动休眠、完整使用后关机、唤醒再开机的实测证据。

代码缺少恢复路径或可能遗留高功耗外设时报告 `P1`；没有电流实测证据时不得声称低功耗验证通过。

---

## 检查结束条件

- 所有 `P0` 已修复并重新检查。
- 每个 `P1` 已修复，或由项目负责人对具体文件、行号和设计意图明确确认。
- 每个 `P2` 已记录处理结论。
- 输出实际执行的搜索、编译、链路推导和硬件验证范围，以及尚未覆盖的限制。
