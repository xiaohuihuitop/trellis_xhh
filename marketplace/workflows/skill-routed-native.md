# 按任务选 Skill 的单 Agent 工作流

本工作流管理 Trellis 任务生命周期，并要求每个任务在规划阶段选择适用的全局 Skill。它不复制、安装或固定绑定任何领域 Skill。

## 职责边界

| 归属 | 负责内容 |
|---|---|
| Trellis | 任务创建、PRD、设计、实现计划、上下文、检查、收尾与项目记忆 |
| 当前任务选择的领域 Skill | 领域事实、实施方法、验证要求与专业门禁 |
| `.trellis/spec/`（可选） | 经项目明确确认、且不应进入全局 Skill 的本地代码特例 |
| README、Doc、原理图、数据手册 | 当前项目真实事实 |

## Skill 路由记录

创建任务后，必须在 `prd.md` 增加以下章节：

```markdown
## Skill 路由

- 必需：`<skill-name>`，原因：<该任务为何必须使用>
- 条件性：`<skill-name>`，触发条件：<何时加载>
- 不使用：<没有适用 Skill 时的原因>
```

- 规划时根据任务领域、风险和当前环境中实际可用的全局 Skill 选择，不因 Workflow 存在而假定某个 Skill 必然可用。
- `必需` Skill 必须在实施前和检查前加载；`条件性` Skill 只在触发条件成立时加载。
- 已记录的必需 Skill 缺失时，报告缺失项并暂停相关阶段，不用未经确认的替代流程。
- Skill 路由随范围变化更新；不要把单次任务的路由写入 `.trellis/spec/`。

### 已知领域映射示例

| 任务类型 | 必需 Skill | 条件性 Skill |
|---|---|---|
| XHH MCU 开发、修复、审查、Demo 复用或硬件事实核对 | `xhh-mcu-development` | 方案存在高风险未决项时使用 `grilling` |
| 重复出现的相同故障 | `diagnosing-bugs` | 修复验证后使用 `trellis-break-loop` 记录经验 |

示例是任务分类规则，不使 Trellis 与其中任何 Skill 形成固定依赖。其他领域任务应按实际可用 Skill 另行选择。

## 任务状态与切换

Trellis 的活动任务按**会话**绑定：同一会话同一时刻只能有一个活动任务；项目内可以保留多个未归档任务。不得根据最近对话猜测当前任务，也不得把普通提问自动并入活动任务。

进入、恢复、切换或收尾任务时，先向用户输出以下状态摘要；读取失败时明确写“未能确定”，不得猜测：

```text
任务：<名称 / 无 / 未能确定>
状态：<planning / in_progress / review / completed / 不适用>
请求分类：<仅讨论 / 直接修改 / 当前任务扩展 / 新任务>
本轮处理：<新建 / 继续 / 请求切换 / 仅讨论 / 收尾>
本轮范围：<一句话>
下一步：<一句话>
```

### 请求分类

分类只用于决定是否需要 Trellis 任务，不能代替领域 Skill 的事实门禁或用户授权。

| 分类 | 判定条件 | 后续动作 |
|---|---|---|
| 仅讨论 | 问答、方案评估、状态查询，未要求改动。 | 不创建、切换或修改任务。 |
| 直接修改 | 单一职责的小范围修复或整理；不新增硬件路径，不改 Flash 数据布局、Event 参数协议或系统状态机，且不跨三个层次。 | 不创建任务；仍按适用领域 Skill 验证。 |
| 当前任务扩展 | 请求仍属于活动任务已记录的目标，但需要补充范围、验收或文件清单。 | 先更新 PRD/design/implement，再实施。 |
| 新任务 | 新功能、迁移、跨三个或更多层次，或涉及 BSP、硬件路径、Flash、Event、协议、状态机、低功耗或新的用户可见行为。 | 说明与活动任务的关系，取得用户许可后创建任务并进入规划。 |

已归档任务不能承接后续需求。新请求即使复用已批准的硬件资源，也必须按上表重新分类；“硬件已批准”只说明可以实现，不等于免除任务规划。

收到新请求时，按以下顺序处理：

1. 先读取当前会话的活动任务及其状态。
2. 若请求属于当前任务已记录的范围，明确标注“继续”，再实施。
3. 若请求是独立工作，先按“请求分类”判断直接修改或新任务。需要新任务时标注“请求切换”，说明当前任务已完成、未完成、阻塞项和恢复下一步；等待用户确认后才创建或选择新任务。
4. 若请求仅为问答、方案讨论或状态查询，标注“仅讨论”，不创建、切换、完成或修改任何任务。
5. 切换任务不等于完成旧任务。旧任务保持其 CLI 支持的原状态，交接信息写入其任务文档；不得虚构 `paused` 等未支持状态。

## 复杂度判定与 Brainstorm

`Brainstorm` 是显式规划步骤，不自动执行，也不能替代 PRD、设计或任务创建。开始新任务或扩大现有范围前，必须判断是否存在以下任一情况：

- 需求、验收条件或外部事实尚未确定；
- 多个可行技术方案需要取舍；
- 涉及多模块、迁移、架构、协议、状态机、安全、低功耗或其他高风险改动；
- 当前项目事实与参考实现、文档或现有代码存在冲突。

命中任一项时，在状态摘要中建议执行 `Trellis Brainstorm`，说明触发原因，并等待用户决定。未命中时可直接进入普通任务规划。Brainstorm 的结论、决策依据和未决项必须回写 `prd.md`；涉及技术方案时同步回写 `design.md`。

## 阶段

```text
Plan -> Skill 路由与事实核对 -> PRD/design/implement -> Execute -> Check -> Finish
```

### Phase 1: Plan

1. 读取当前会话任务并输出状态摘要，完成请求分类、任务切换判定和 Brainstorm 判定。
2. 按 Trellis 规则取得创建或切换任务的用户许可后，再创建或选择任务。
3. 在 `prd.md` 记录范围、约束、验收条件、已确认事实、未决项和 Skill 路由。
4. 复杂任务在实施前完成 `design.md` 与 `implement.md`。`design.md` 记录边界、调用链与取舍；`implement.md` 记录修改顺序、验证方法和回退点。
5. 领域事实缺失或冲突时，先加载已选择的领域 Skill；仍无法确认时在 PRD 记录证据与阻塞项，并向用户确认。
6. 高风险且方案未决时，按 Skill 路由加载 `grilling`。结论和未决项必须回写 `prd.md`；涉及技术方案时同步回写 `design.md`。

### Phase 2: Execute

1. 仅在任务状态进入 `in_progress` 后实施。
2. 实施前加载 PRD 中所有必需 Skill，并读取 PRD/design/implement；项目存在经确认的本地 `.trellis/spec/` 特例时，额外读取相关内容。
3. 只修改当前任务必需的文件和调用链；领域事实未闭环时，只实施不依赖该事实的部分，或停止并请求确认。
4. 同类问题连续失败时，按 PRD 路由加载诊断 Skill；已验证修复后，才更新项目记忆。
5. 用户提出超出当前范围的新请求时，重新执行“任务状态与切换”规则；未明确为继续前，不得混入当前实现。

### Phase 3: Check And Finish

1. 检查前再次加载 PRD 中所有必需 Skill，按其要求核对领域事实、修改范围和验证结果。
2. 将代码验证、事实确认和实物或运行验证分别记录；不得以单一验证结果替代其他验证结论。
3. 仅当项目存在经确认的本地特例，且该特例不属于全局 Skill 职责时才更新 `.trellis/spec/`；不得复制全局 Skill 的规则。
4. 收尾前在 `implement.md` 写入以下最小记录：检查范围、构建或测试结果、事实确认状态、实物或运行验证状态、最终提交和未决项；再更新任务文档中的完成项与 Skill 路由，完成检查后按用户授权提交。
5. 输出“收尾”状态摘要，明确任务是否已完成、仍待验证，及归档是否已执行；不得把未验证事项表述为完成。

## 工作流状态

[workflow-state:no_task]
先输出“无任务”的状态摘要和请求分类，再判断是否需要 Trellis 任务。直接修改可按适用领域 Skill 实施；新任务、复杂开发、迁移或审查任务先进行复杂度判定、取得用户许可，再创建任务并进入规划；普通问答标注“仅讨论”，不创建任务。
[/workflow-state:no_task]

[workflow-state:planning]
保持规划阶段。先输出当前任务状态摘要；在 PRD 记录 Skill 路由、项目事实和验收条件；复杂任务完成 design.md 与 implement.md。高风险未决方案按路由加载对应 Skill，结论回写任务文档后才能 start。
[/workflow-state:planning]

[workflow-state:planning-inline]
保持规划阶段。先输出当前任务状态摘要；在 PRD 记录 Skill 路由、项目事实和验收条件；复杂任务完成 design.md 与 implement.md。高风险未决方案按路由加载对应 Skill，结论回写任务文档后才能 start。
[/workflow-state:planning-inline]

[workflow-state:in_progress]
实施与检查前输出当前任务状态摘要，并加载 PRD 中的必需 Skill，读取任务文档和经确认的本地 Spec 特例（如存在）。事实缺失时停止相关实现；范围变化时先执行任务切换判定；重复失败按路由诊断，验证修复后再更新项目记忆。完成检查和任务文档收尾后，按用户授权提交。
[/workflow-state:in_progress]

[workflow-state:in_progress-inline]
实施与检查前输出当前任务状态摘要，并加载 PRD 中的必需 Skill，读取任务文档和经确认的本地 Spec 特例（如存在）。事实缺失时停止相关实现；范围变化时先执行任务切换判定；重复失败按路由诊断，验证修复后再更新项目记忆。完成检查和任务文档收尾后，按用户授权提交。
[/workflow-state:in_progress-inline]

[workflow-state:completed]
先输出“收尾”状态摘要。任务已完成时，确认任务文档、验证结论与提交状态一致，再执行归档；新请求必须重新走任务分类，不得自动并入已完成任务。
[/workflow-state:completed]
